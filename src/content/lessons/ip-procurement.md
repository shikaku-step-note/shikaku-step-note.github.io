## 実現したいことを先に決める

システム化計画では目的、対象範囲、費用、効果、体制、期間、リスクを整理します。実現可能性を技術・費用・運用等から検討するのがフィージビリティスタディです。効果を測る基準がなければ、完成後に投資を評価できません。

## 要件を具体化する

業務要件は仕事として実現すべき内容、機能要件はシステムが行う処理です。非機能要件には性能、可用性、セキュリティ、運用性、移行性などがあります。「使いやすい」「速い」では判断が分かれるので、想定利用者、処理件数、応答時間の測定条件等を明らかにします。利害関係者の認識をすり合わせ、変更の承認手順も決めます。

## 調達の流れ

| 文書・工程          | 目的                                       |
| ------------------- | ------------------------------------------ |
| RFI（情報提供依頼） | 市場や選択肢の情報を集める                 |
| RFP（提案依頼）     | 要件・条件を示して具体的な提案を求める     |
| 見積り・提案評価    | 費用、品質、運用、支援などを比較する       |
| 契約・受入れ        | 成果物、責任、検収条件、権利等を明確にする |

## 例：予約システムの要件

「予約を登録できる」は機能です。「営業時間中、同時100人の利用で検索応答2秒以内」は測定条件付きの性能要件です。候補企業の実績や標準機能をRFIで調べ、対象業務と評価基準をRFPにまとめます。最安値だけで決めず、移行、データの持出し、障害時対応も比べます。

## まとめ

目的→要件→提案比較→合意→受入れのつながりを保ちます。何をもって完成とするかを、実装前から明確にしましょう。

## 要求を受入条件に変える

予約サービスで「混雑時でも快適に使える」と言われたら、誰が何をどの状態で利用するかを確認します。例えば「同時100人で、空き検索の95％が2秒以内」と定義すると測れます。検索できるという機能と、応答時間や可用性などの非機能条件を分け、測定対象、環境、合格条件を共有します。要求を決める担当と受入を行う担当が違うときも、同じ条件で判断できる形にします。

候補製品の情報を広く集める段階ではRFI、実現方法と見積りを具体的に提案してもらう段階ではRFPを使います。評価表には対象範囲、必須条件、費用、保守、データ移行などを置きます。A社に移行作業が含まれ、B社に含まれないなら、見積総額の比較前に範囲をそろえます。

初期80万円、年運用20万円と、初期30万円、年運用38万円を3年使う例では、前者140万円、後者144万円です。ここでは他費用を無視しています。解約費や職員の研修などがあれば、実際の判断では別に見積もります。

## 三つの資料を照合し、提案の良し悪しを決める

### 現状メモを、測れる要求と制約に変える

貸出窓口の現状メモには『昼休みに行列ができる』『同じ機器を二人が予約できる』と書かれています。業務上の狙いは、窓口へ来なくても予約でき、重複を防げることです。『利用者は空いている機器を一覧から選び、同じ時間帯の重複予約を確定できない』は機能要件の一例です。一方、『平日の昼休みに100人が同時に操作しても、空き状況の表示が95％以上の操作で2秒以内』は性能要件です。機能と制約を分けると、同じ操作でも何を合格条件とするか明確にできます。

システム化計画では、予約機能を先行し、保守契約は後で範囲を分ける、紙受付を一定期間残すなど、対象範囲、体制、費用、リスクを決めます。業務要件を定義するときは、誰が使い、どんなデータを入力し、誰が承認するかを現状調査から洗い出します。予約を取消せる期限、代理予約の扱い、通信障害時の窓口のように、通常ケース以外で運用を続けられるかも考えます。

### 初期費用が安い提案をそのまま採用しない

利用可能な方式や相場が分からなければ、事業者へRFI（情報提供依頼）を出して、候補と制約を把握できます。比較できる形で提案を求めるRFP（提案依頼）では、要件、評価基準、提出内容、期限をそろえます。提案に『高速』とだけ書かれていたら、同時利用者数、操作、時間の測り方がRFPと一致しているか確認します。測定条件を各社で変えると、性能点を公平に付けられません。

方式Aは初期40万円、月3万円。方式Bは初期64万円、月1万円で、どちらも機能と性能の必須条件を満たすとします。18か月ではAは94万円、Bは82万円です。初期費用だけならAが安く、18か月ならBが安くなります。12か月で両者が76万円となるので、利用期間によって順位が変わります。さらに保存データの移行費用、障害時の支援、契約終了後の取出しなど、見積りに含まれない作業を確認します。必須条件に不足がある場合は費用比較だけで補えません。

### 総合演習：開館時の混雑対策を、要求書・見積り・試験記録から決める

市の資料室が、閲覧席の予約をオンラインで受け付けようとしています。以下は教材用の資料です。どの提案を選ぶか、単価を見る前に必須条件を照合してください。

| 資料 | 確認する内容 |
| --- | --- |
| 現状調査 | 開館直後に電話予約が集中する。同じ席と時刻を二人へ案内する事故がある。窓口予約は残す。 |
| 提案依頼 | ①同じ席と時刻は一人まで。②電話で取った予約とWebの予約は同じ台帳で管理。③初期・運用を含む24か月の費用は120万円以下。 |
| A社の提案 | 初期30万円、月2万円。電話とWebは別の台帳を使い、夕方に一日分を同期する。 |
| B社の提案 | 初期48万円、月2.5万円。電話とWebが同じ台帳に書き込み、確定時に重複を拒否する。 |
| C社の提案 | 初期20万円、月5万円。電話とWebは同じ台帳を使用し、確定時に重複を拒否する。 |

まずA社の24か月費用は30＋2×24＝78万円です。安価ですが、夕方まで二つの台帳が別々なので、昼間に電話とWebから同じ席を確定できるおそれがあります。要件①②を満たせません。B社は48＋2.5×24＝108万円で予算内です。提案の記述は必須条件を満たします。C社は20＋5×24＝140万円なので、機能が合っても③で候補から外れます。**必須条件で候補を絞り、残った候補の優劣を評価する**と、安さで欠けた機能を埋め合わせてしまうことを防げます。

次に、選んだB社の試験記録に「Web予約を一件作成し、Webの一覧に表示された」とあります。この試験で確かめたのは、一件の登録と表示です。電話窓口で席を予約するのと同時に、Webから同じ席・同じ時刻を送ります。どちらか一方だけが確定し、拒否された側に別の席を選べる案内が出て、最終的な台帳の件数も一件であることを確認します。異なる時刻や席を選んだ場合は、両方とも確定することも確かめます。過剰に拒否する設計でも利用者に影響が出るからです。

見積り期間が36か月に変わると、B社は48＋2.5×36＝138万円です。予算が据え置きなら、以前の選定結果はそのまま使えません。評価結果には金額に加えて「何か月分を含むか」「要件をどこまで固定したか」を残します。適合する案がなくなった場合は、根拠なく基準を外すのではなく、費用条件や期間の見直しを発注者の判断に戻します。

出題範囲の参照：[IPA ITパスポート試験シラバス Ver.6.5（本文25ページ）](https://www.ipa.go.jp/shiken/syllabus/omgdg50000005kn1-att/syllabus_ip_ver6_5.pdf)。

## 導入計画から切替え、受入れ、契約終了まで考える

新しい受付システムへ300件の既存データを移す例です。まず移行対象、正本、変換規則、照合項目を決めます。件数が300件で一致しても、同じ1件を重複し別の1件を落としている可能性があります。識別番号の重複、件数、金額や日付の照合、例外の確認を組み合わせます。切替え中の新規受付は、旧環境に書き込むか別台帳に残すかを決め、復旧時の二重登録を防ぎます。

### 例題：要件を試験できる条件に変える

要望に「受付を速く」とある場合、どの操作をどんな負荷で測るかがありません。「同時利用者30人の試験で、登録操作の95％を2秒以内に終える」のように、場面、対象、測定と合格条件を示します。法令や既存契約から来る必須条件と、予算次第で後回しにできる要望を区別します。変更があれば、費用、期限、既に作った試験項目への影響を評価して、利用部門と合意します。

調達では提案価格だけでなく、運用保守、データ移行、契約終了時のデータ返却、機器の電力消費や廃棄方法も条件をそろえて比較します。データ返却に関しては、形式、移行に要する期間、返却後の削除を取り決めます。提案段階に書いた条件を受入試験と契約に反映できているか確認します。

| 検査する観点 | 件数だけで判定できるか |
| --- | --- |
| レコード全体の数 | できる |
| 同一IDの重複と別IDの欠落 | できない |
| 変換後の金額の正しさ | できない |

### 見積りの対象をそろえて費用を比較する

案Aの初期費は100万円、年間費は30万円、契約終了時のデータ抽出は別途20万円です。案Bは初期140万円、年間15万円で抽出費は年額に含みます。3年間の利用ではAが210万円、Bが185万円です。利用年数が変わると差も変わります。前提に含める作業の範囲と期間をそろえ、費用以外の必須条件も検討します。バックアップの復元試験、データを取り出すための形式、機器の廃棄方法は提案書と契約の両方に反映します。

<span id="textbook-procurement-contract"></span>

### 調達条件を、比較できる記録と契約へ落とす

機器の電力消費を選定条件にする場合、仕様書に「環境に配慮」とだけ書くと、各社が別の基準を使うため比較しにくくなります。稼働時と待機時の消費電力、測定条件、想定台数と運用時間をそろえます。例えば機器20台について消費電力が1台10 W違い、年間2,000時間使用するなら、差は20×10×2,000＝400,000 Wh＝400 kWhです。廃棄、修理部品の供給、交換頻度にも条件があれば別に評価します。

AIを使う分析サービスを調達するときは、利用者が提供するデータ、事業者が加えるデータ、出力される結果を区別します。提供データを今回の分析だけに使えるのか、別の顧客向けに学習してよいのか、契約終了時に何を返却・削除するのかを、利用目的と権限の表で確かめます。精度の評価には、試験のデータ、誤りの種類、受入れ条件も明記します。

環境基準の参考： [環境省のグリーン購入法案内](https://www.env.go.jp/policy/hozen/green/g-law/)（2026年11月12日確認）。

### 利用者の要求と測定条件をそろえる

担当者は「月末にもスムーズに締め処理したい」と話しました。調査の結果、月末は明細が最大8万件で、集計結果を18時までに確認する必要があると分かりました。機能要件は対象月の明細を集計し、明細と合計を確認できることです。非機能要件には、例えば明細8万件の集計が所定の環境で30分以内に終わることを入れます。実データには欠損や重複があるかを調べ、エラーの扱いも合意します。

利用者が対象の部門を追加したら、明細件数、締め時刻、試験に使うデータ、移行期間に影響が出るかを比較します。追加の機能に合意しただけで、試験条件を古いままにすると、新しい負荷での性能を確かめられません。
