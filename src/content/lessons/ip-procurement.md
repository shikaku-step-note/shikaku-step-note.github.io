## 実現したいことを先に決める

システム化計画では目的、対象範囲、費用、効果、体制、期間、リスクを整理します。実現可能性を技術・費用・運用等から検討するのがフィージビリティスタディです。効果を測る基準がなければ、完成後に投資を評価できません。

## 要件を具体化する

業務要件は仕事として実現すべき内容、機能要件はシステムが行う処理です。非機能要件には性能、可用性、セキュリティ、運用性、移行性などがあります。「使いやすい」「速い」では判断が分かれるので、想定利用者、処理件数、応答時間の測定条件等を明らかにします。利害関係者の認識をすり合わせ、変更の承認手順も決めます。

## 調達の流れ

| 文書・工程          | 目的                                       |
| ------------------- | ------------------------------------------ |
| RFI（情報提供依頼） | 市場や選択肢の情報を集める                 |
| RFP（提案依頼）     | 要件・条件を示して具体的な提案を求める     |
| 見積り・提案評価    | 費用、品質、運用、支援などを比較する       |
| 契約・受入れ        | 成果物、責任、検収条件、権利等を明確にする |

## 例：予約システムの要件

「予約を登録できる」は機能です。「営業時間中、同時100人の利用で検索応答2秒以内」は測定条件付きの性能要件です。候補企業の実績や標準機能をRFIで調べ、対象業務と評価基準をRFPにまとめます。最安値だけで決めず、移行、データの持出し、障害時対応も比べます。

## まとめ

目的→要件→提案比較→合意→受入れのつながりを保ちます。何をもって完成とするかを、実装前から明確にしましょう。

## 要求を受入条件に変える

予約サービスで「混雑時でも快適に使える」と言われたら、誰が何をどの状態で利用するかを確認します。例えば「同時100人で、空き検索の95％が2秒以内」と定義すると測れます。検索できるという機能と、応答時間や可用性などの非機能条件を分け、測定対象、環境、合格条件を共有します。要求を決める担当と受入を行う担当が違うときも、同じ条件で判断できる形にします。

候補製品の情報を広く集める段階ではRFI、実現方法と見積りを具体的に提案してもらう段階ではRFPを使います。評価表には対象範囲、必須条件、費用、保守、データ移行などを置きます。A社に移行作業が含まれ、B社に含まれないなら、見積総額の比較前に範囲をそろえます。

初期80万円、年運用20万円と、初期30万円、年運用38万円を3年使う例では、前者140万円、後者144万円です。ここでは他費用を無視しています。解約費や職員の研修などがあれば、実際の判断では別に見積もります。
